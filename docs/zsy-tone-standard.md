# 文风标准 v1.0.0（Tone Standard）

> **状态：已发布。** 这份文档是「文风」这件事在本网关上的**定义处** ——
> 取值有哪些、各自什么意思、字段怎么约束、以及**将来怎么演进**。
>
> 它有两个读者：
>
> | 读者 | 读它干什么 |
> |---|---|
> | **写客户端的人**（例如 `aimv-studio` 的文本工程） | 知道该发什么、该收什么、遇到不认识的取值怎么办 |
> | **维护词表的人**（以后改这一套的人） | 知道哪些改动是允许的、哪些会打断别人 |
>
> ⚠ 这份文档**不是**接口文档。请求怎么发、响应长什么样，看
> [`zsy-toneplaza-api.md`](./zsy-toneplaza-api.md)。
>
> ★ 本文的**机器可读版本**是 `GET /api/zsy/tone/standard`（公开、可缓存）。
> 两边说的是同一件事，而**代码那一份是权威**：词表声明在
> `zsy/tone/standard.go`，本文与它由测试盯着
> （`zsy/tone/standard_test.go` 的 `TestToneStandard_PublishesBothVocabularies`
> 逐值比对，且上限是**拿真值去撞校验器**验出来的，不是抄常量）。

## 1. 一句话

**一条文风 = 一段可以原文拼进系统提示的写作指令，加一份「它用起来是什么样」的示范。**

它区别于音色与形象的地方在这里：

| | 音色 | 形象 | **文风** |
|---|---|---|---|
| 载体 | 一段音频 | 一张脸 | **一段文字指令** |
| 怎么被感知 | 试听 | 看 | ★ **靠一组共用同一段原文的改写对照**（§6） |
| 有没有媒体文件 | 有 | 有 | **没有**（所以没有上传接口） |

## 2. 版本与兼容性

当前版本：**`1.0.0`**（`ToneStandardVersion`）。

### 2.1 五条承诺

这五条同时出现在接口响应的 `compatibility` 字段里 —— 规则跟着数据走，
不只活在这个仓库里。

| # | 条款 | 措辞强度 |
|---|---|---|
| 1 | 已发布的取值**不得**改名、**不得**删除 | 必须（MUST NOT） |
| 2 | **可以**新增取值；新增不属于破坏性变更 | 可以（MAY） |
| 3 | 空值**始终**表示「未分类 / 未指定」 | 必须（MUST） |
| 4 | 客户端**必须**容忍不认识的取值：照原样显示，**不得**丢弃该条目 | 必须（MUST） |
| 5 | 版本号**只在形状变化时**前进（新增字段或调整上限）；新增取值**不**前进 | 必须（MUST） |

### 2.2 第 4 条为什么单独拎出来说

因为它是**最容易写错、也最贵**的一条。

一个客户端如果把不认识的取值过滤掉，那么本网关每次**正常的词表扩充**，
在它眼里都会表现成**数据丢失**（"广场上怎么少了一半"）。
于是第 2 条（可以新增）就变成了空话 —— 谁都不敢加。

正确的做法是回落成原始值：

```js
// 认识就用本地化标签，不认识就把取值照原样显示
return option ? option.labelKey : value
```

参考实现：`aimv-studio` 的 `src/core/voiceCatalog.js` 就是这么写
（那边的词表没有接口可拉，只能硬编码，所以那条纪律对它更关键）。

### 2.3 版本号什么时候动

| 变化 | 版本 | 例子 |
|---|---|---|
| 新增一个类别或语气取值 | **不动** | 加一个 `Category: "legal"`（合同、法务） |
| 新增一个字段 | 动 | 加 `audience`（目标读者） |
| 调整任何一个上限 | 动 | `prompt` 从 8000 提到 12000 |
| 改一个取值的**含义**但不改名字 | 动，且要在本文记一笔 | 少见，能不改就不改 |
| 修正一个 label 的错别字 | 动（形状没变，但发布物变了） | `labelEn: "Solem"` → `"Solemn"` |

## 3. 类别词表（`category`）

**「这是哪一类写作」** —— 操作员归档一条文风时选它，调用方选它时问的是
"我今天在写什么"。

| 取值 | 中文 | English | 什么时候用它 |
|---|---|---|---|
| `literary` | 文学 | Literary | 小说、散文、随笔 —— 以感受与叙事为主 |
| `business` | 商务 | Business | 方案、汇报、邮件 —— 以推进事情为目的 |
| `academic` | 学术 | Academic | 论文、综述、研究报告 —— 要求可核查 |
| `media` | 媒体 | Media | 新闻、特稿、评论 —— 面向公众发布 |
| `spoken` | 口播 | Spoken | 口播稿、播客、讲稿 —— 要念出来 |
| `technical` | 技术 | Technical | 文档、教程、说明 —— 以准确为先 |
| `marketing` | 市场营销 | Marketing | 文案、种草、品牌故事 —— 以转化为目的 |

⚠ **它划的是"交付场景"，不是"文体学分类"。** 一份写得像散文的产品介绍，
操作员该按它的**用途**归到 `marketing`（它要被用来卖东西），
而不是按它的**笔法**归到 `literary`。理由是调用方找文风时想的是用途：
"我要写一封邮件"比"我要写一篇散文式的文本"常见得多。

---

## 4. 语气词表（`tone`）

**「用什么调子说」** —— 与 `category` 正交：同一个类别下，各个语气都该有。

| 取值 | 中文 | English | 什么时候用它 |
|---|---|---|---|
| `warm` | 温暖 | Warm | 有体温、有体谅，先接住情绪再讲事情 |
| `calm` | 冷静 | Calm | 降速、去形容词，让事实自己说话 |
| `sharp` | 犀利 | Sharp | 短句、直给，敢下判断，不为冒犯道歉 |
| `humorous` | 幽默 | Humorous | 靠反差与自嘲取胜，不靠谐音梗 |
| `solemn` | 庄重 | Solemn | 有分量、少口语，适合需要被记住的场合 |
| `lively` | 活泼 | Lively | 节奏快、有动作感，像在跟人当面聊天 |
| `plain` | 平实 | Plain | 把话说清楚就走，不修饰、不表演 |

⚠ **`plain`（平实）是默认的那一档**：一条文风如果不确定该归哪个语气，
`plain` 比留空更有用 —— 留空表示"这条还没分类"，而 `plain` 表示
"它就是要平实"。两者含义不同，别混。

## 5. 字段契约

| 字段 | 类型 | 必填 | 上限 | 说明 |
|---|---|---|---|---|
| `name` | string | ✅ | 191 | 文风名称，**全库唯一** |
| `description` | string | — | 2000 | 一句话说明它适合什么 |
| **`prompt`** | string | ✅ | **8000** | ★ **写作指令正文** —— 见 §5.1 |
| `category` | enum | — | — | §3；空 = 未分类 |
| `tone` | enum | — | — | §4；空 = 未指定 |
| `language` | string | — | 16 | 语言短标签（`zh`、`en`、`pt-br`）。**开放取值**，见 §5.2 |
| `scenes` | string[] | — | 8 × 24 | 「适合场景」标签；分隔符 `,` `，` `、` `;` `；` `\|` |
| `sampleInput` | string | — | 4000 | 示例原文 —— 见 §6 |
| `sampleOutput` | string | — | 4000 | 按本文风改写后的样子 —— 见 §6 |
| `enabled` | bool | — | — | 上架开关；新建默认 `true` |
| `sortOrder` | int | — | ±1000000 | 广场排序；并列时按 id 升序 |

### 5.1 `prompt` 必须是**指令**，不是**描述**

这是本标准的**核心条款**。

| ✅ 应该写 | ❌ 不该写 |
|---|---|
| "以克制、平视的笔调写作：多用短句，少用形容词……" | "一种克制、平视的文风" |

理由：`prompt` 会被调用方**原文拼进系统提示**，不做二次加工。
一句"描述"（"一种克制的文风"）对模型输出的影响，远小于一句"指令"
（"多用短句，少用形容词"）—— 而两者在广场上看起来一样像回事。
**界面会显得对，效果会不对**，而且没有报错。

所以校验是硬的：`prompt` 不能为空（`文风提示词不能为空`）。
种子数据另有一条守卫（`TestSeedCSV_InstructionsAreInstructionsNotDescriptions`）
逐条检查它读起来是不是祈使句。

### 5.2 `language` 是**开放**取值，不进词表

与 `category` / `tone` 不同，`language` **不发布受控词表**，只约束**形状**：
小写字母开头，可含数字、`-`、`_`（正则 `^[a-z][a-z0-9_-]*$`，长度 ≤ 16）。

理由是别人给语言起名的花样太多：`mx`（墨西哥西班牙语）、`tl`（他加禄语）
都是真实存在的写法，一个封闭词表只会拒掉下一个。
显示的时候用运行时的 `Intl.DisplayNames` 就够了 —— 认识就显示语言名，
不认识就照原样显示取值（这正是 §2.1 第 4 条那条纪律）。

## 6. 示例对照约定（`sampleInput` / `sampleOutput`）

### 6.1 约定本身

> **同一次维护里，多条文风**应当**共用同一段 `sampleInput`**，
> 各自的 `sampleOutput` 是它按本文风改写后的样子。

一条文风应当**同时**给出这两个字段，或同时不给。

### 6.2 为什么这条是标准的一部分

因为**文风既不能试听，也不能看脸**。

音色有示例音频（点一下就听到），形象有图（点开就看到）。
文风两样都没有 —— 一条文风在卡片上就是一段名字、一段简介、一段提示词。
用户凭什么在广场上挑？只能凭名字和形容词，那与随机选没有区别。

共用同一段原文解决了这件事：**十条文风对同一段话的十种改写法并排放在一起，
差异一眼就看得见**，而这是文风唯一能被感知的方式。

★ 还有一笔账：这份对照是**存下来的，不是生成的**。
所以浏览整个广场**不花一分钱**、不调任何模型。
（"用你自己的句子试写一遍"是调用方的功能，不是这张表的事 —— 见 §8 墓碑。）

### 6.3 它是**约定**，不是**约束**

接口**接受**没有示例的行，也接受各写各的示例 —— 操作员一次只维护一条文风时，
要求他遵守这条是没道理的。

所以标准只在**能被提醒的地方**提醒：

- CSV 导入时：文件的示例原文有多个不同写法 → 回一条 warning（不是错误）
- CSV 导入时：有行缺示例 → 回一条 warning
- 种子数据：由 `TestSeedCSV_SharesOneSampleInput` 等**硬性守住**（种子是示范）

一条会**拒绝**不合规文件的硬约束，只会教会大家把那一列留空。

## 7. 怎么用它

### 7.1 程序化读取（推荐）

```http
GET /api/zsy/tone/standard
```

返回本文的机器可读版本：`version` / `categories` / `tones` / `limits` /
`compatibility` / `examplePair`。

⚠ 这是公开接口里**唯一可缓存**的一个（`Cache-Control: public, max-age=3600`）——
它的内容只在发新版本时才变。而 `GET /api/zsy/tone/list` 是 `no-store`，
因为目录是**可变数据**，绝不能缓存。

客户端应该在启动时拉一次，用它渲染筛选器与表单校验的边界，
而**不是**把词表抄一份到自己的代码里。抄一份的代价有实测记录：
本仓库的 `docs/zsy-voiceplaza-api.md` 与消费方
`D:\MV项目\aimv-studio\docs\15` §3.3 记着同一件事 ——
音色与形象共用 `gender` / `ageRange`，而因为接口不发布词表，客户端只能各存一份，
最后只能靠一条"断言两边是同一个对象"的测试来维持一致。

### 7.2 人读

本文。以及 `GET /api/zsy/tone/standard` 的 JSON（浏览器直接打开就是）。

### 7.3 参考实现

`seedmodel/toneplaza-tones.csv` —— **18 条文风，覆盖全部 7 个类别 × 7 种语气**，
共用同一段示例原文。

它不是"随便几条样例"，而是**这份标准的示范**：

| 守卫 | 守的是什么 |
|---|---|
| `TestSeedCSV_ImportsThroughTheProductionPath` | 走生产的 CSV 路径能干净导入（无 warning、无失败行） |
| `TestSeedCSV_CoversEveryPublishedVocabularyValue` | 每个已发布取值都有示例 |
| `TestSeedCSV_SharesOneSampleInput` | 真的共用同一段原文（§6） |
| `TestSeedCSV_OutputsAndPromptsAreDistinct` | 没有两条是"两个名字一条文风" |
| `TestSeedCSV_InstructionsAreInstructionsNotDescriptions` | `prompt` 都是指令（§5.1） |

灌库：

```bash
go run ./_scripts/toneplaza-seed -dry     # 先看它怎么说，不写库
go run ./_scripts/toneplaza-seed          # 按 name upsert
go run ./_scripts/toneplaza-seed -replace # 清空重建（在一个事务里）
go run ./_scripts/toneplaza-seed -stats   # 看存量和词表覆盖情况
```

⚠ 这个命令**默认要求词表覆盖完整**：种子是标准的示范，少一个取值就退出非零。
导入一份有意精简的目录时要显式加 `-allow-partial`。

## 8. 演进：怎么加一个取值

1. 在 `zsy/tone/standard.go` 的两个表之一里加一条
   （`standardCategories` / `standardTones`）
2. 同时在 `models.go` 的 `allowedCategories` / `allowedTones` **和**
   `AllowedCategories` / `AllowedTones` 两个切片里加它
   （前者是校验用的 map，后者是有序的发布视图；
   `TestToneStandard_PublishesBothVocabularies` 盯着它们一致）
3. 在 `seedmodel/toneplaza-tones.csv` 里补至少一条用这个取值的文风
   （否则 `TestSeedCSV_CoversEveryPublishedVocabularyValue` 会红）
4. 在本文 §3 / §4 的表里加一行
5. **不要**动 `ToneStandardVersion`（§2.3：新增取值不前进）
6. 已有客户端**不需要**改（§2.1 第 4 条：它们必须已经能容忍不认识的取值）

### 墓碑：明确不做

| 不做 | 为什么 |
|---|---|
| **不做受控的 `language` 词表** | §5.2。开放的短标签，显示交给 `Intl.DisplayNames` |
| **不做"用你自己的句子试写"这个接口** | 那是调用方的功能（要花钱、要选模型），不是这张表的事。本表只存**示范对照** |
| **不做文风的版本历史 / 回滚** | 目录是编辑内容，不是审计记录（与 `zsy_voice` / `zsy_avatar` 同一条：行是**硬删**的） |
| **不做"文风的继承 / 组合"**（A 文风 = B + 一点变化） | 看着省事，实际会让"这条文风到底是什么"变得说不清。宁可贵一点、写清楚 |
| **不做把 `prompt` 拼装成完整系统提示** | 拼接是**调用方**的事（它还知道自己的体裁、字数、读者）。这张表交出去的是**一段风格指令**，不是一份完整的提示词 |
